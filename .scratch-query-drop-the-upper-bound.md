# `isabelle-query`'s dependency cap excludes the first `isabelle-layout` release

```toml
# now
dependencies = ["isabelle-layout>=0.1.0,<0.2.0"]

# needed
dependencies = ["isabelle-layout>=0.2.0"]
```

**This is blocking, and it needs doing before `isabelle-layout` uploads.** The
first release on PyPI is **0.2.0**, and `0.2.0` does not satisfy `<0.2.0`.
Neither 0.1.0 nor 0.1.1 was ever published, so there is no earlier version to
resolve to — `pip install isabelle-query` will fail to find any
`isabelle-layout` at all.

The version is 0.2.0 because it adds a console script, `isabelle-layout`, which
is a feature. Nothing was removed and no behaviour changed; your 874 tests pass
against it unmodified.

Also, for the release checklist:

> `todo.md:16` — "publish `isabelle-layout` 0.1.0 first, then cut …"

should read **0.2.0**. 0.1.0 is never coming.

## The cap, which is the underlying thing

The stated reason is a good instinct and deserves an answer rather than a
dismissal:

> Upper bound because the dependency is pre-1.0: 0.x minors may break, and a
> parser this tool's every answer rests on is not somewhere to discover that
> from a user's traceback.

### What just happened is the argument in miniature

The cap has now excluded **every published release of the package it
constrains** — one for one — while protecting against nothing, because there
was never a prior version to fall back to. That is not bad luck; it is what an
upper bound does by construction. It cannot distinguish "0.2.0 broke something"
from "0.2.0 exists", because it is evaluated before anything is run.

### A cap does not detect a break; it prevents an install

The failure being guarded against — finding out from a user's traceback — is
prevented by *running your suite against the new version*, which you already
do. A range only decides **when you are allowed to find out**, and a cap makes
that later and all at once: nothing is checked until someone relaxes the
number, at which point every accumulated change arrives together. Continuous
exposure is strictly more informative than a ceiling.

Concretely: `isabelle-query`'s 874 tests pass against 0.2.0 today, including
the `[session-dirs]` load-set changes. That check is the protection. The cap
contributed nothing to it.

### The specific risk is smaller here than pre-1.0 usually implies

`isabelle-layout`'s public surface is pinned by a test (`test_public_api.py`)
whose whole purpose is that a name cannot leave the surface quietly — that is
the `isabelle_query.common` failure it was written to prevent. So "a 0.x minor
silently removes something you import" is not really the available failure
mode; a removal fails loudly upstream and is a deliberate act. `SessionInfo`'s
field names and types are contractual under `[session-info]`. What *can* still
change is behaviour, and behaviour is what your suite covers.

The README now states this explicitly under **Compatibility**, so it is a
promise you can point at rather than an assumption you have to make.

### The cap propagates, which is what matters for this pair

`isabelle_query.common` re-exports `isabelle-layout`. So the ceiling is not
only yours: every consumer of `isabelle-query` inherits it, and a project that
needs `isabelle-layout` 0.3 for its own reasons cannot also install
`isabelle-query` — without having chosen that constraint or being able to
override it.

That is exactly the coupling the split was performed to remove, reappearing one
level down. The argument for splitting was that a library shipped inside an
application can only be adopted by people willing to adopt the application; a
capped re-export re-creates that in the resolver instead of the import path.

### What to do instead

- **Floor only**: `isabelle-layout>=0.2.0`.
- **Test against latest.** CI running your suite against the released
  `isabelle-layout` *and* against its `main` finds a break before a release
  rather than after one — which is what the cap was reaching for.
- **Constrain on evidence, not on principle.** If some future version does
  break something, add `!=0.4.0` or raise the floor *then*, with a reason
  recorded. A specific exclusion with a known cause is far more useful to a
  reader than a pre-emptive range.

## What this side did

`isabelle-layout`'s README now carries a **Compatibility** section stating what
is promised — `__all__` pinned by a test, `SessionInfo`'s field names and types
as the contract, new attributes appended with defaults, no runtime
dependencies. Asking you to drop a guard is only fair if the thing you were
guarding against is written down rather than assumed. If anything there is
weaker than you need in order to drop the ceiling, say which, and it can be
made explicit.
